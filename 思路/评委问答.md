# 灵窗智控 · 物联网大赛评委问答

> 用途：答辩准备 / 评委提问预案
> 角色：物联网大赛专业评委视角
> 说明：以下问题均基于项目实际架构与实现整理，答案可直接用于现场答辩。

---

## 项目概览

灵窗智控是一套 **多传感器融合的多模式智能窗户/百叶窗控制系统**，采用「边缘设备 + 云中继 + Web 前端」三层架构：

- **设备端**：ESP32-P4（360MHz 双核 RISC-V + 32MB PSRAM）主控 + ESP32-C6（WiFi 6/BT 协处理器，SDIO 互联）
- **感知层**：室内/室外双温湿度（SHT3x）、光照（BH1750）、烟雾/雨水（ADS1115 ADC）、气流风速（微型马达发电 + ADC）
- **执行层**：6 路舵机（4 路百叶 + 2 路雨棚，MCPWM 驱动）
- **交互层**：7 寸 MIPI-DSI 触控屏、本地语音识别（唤醒词 + 命令词）、TTS、摄像头视频流
- **控制模式**：手动 / 环境感知 / 用户自适应 / 定时 / 自然风，共五种
- **云端**：Python WebSocket 中继 + 天气推送 + DeepSeek 增强（NLP 与穿搭建议）

---

## 一、总体架构与芯片选型

**Q1：为什么采用 ESP32-P4 + ESP32-C6 双芯片，而不是直接用一颗自带 WiFi 的 ESP32-S3？P4 本身没有无线能力，靠 C6 走 SDIO 扩展复杂度很高，代价换来了什么？**

答：核心价值在于 P4 的**边缘计算能力**——360MHz 双核 RISC-V、32MB PSRAM、MIPI-DSI/CSI 接口、硬件 JPEG 编码器与 DSP 指令扩展。本项目需同时承载 7 寸高清 LVGL 界面、1080P 摄像头、本地语音识别（AFE + WakeNet + MultiNet）以及多路传感器融合与六路舵机控制，单颗 S3 的算力、内存与外设接口均不足。C6 专职 WiFi 6/BT，通过 SDIO 将通信卸载到协处理器，使 P4 主核专注应用。这是「算力芯片 + 通信芯片」的明确职责分离。

**Q2：设备、云服务器、浏览器之间为什么用 WebSocket 中继，而不是 MQTT 或 WebRTC？**

答：首要目标是解决设备位于 NAT 之后的外网可达性问题。中继服务器（`ws://47.105.45.239:8765`）让任意位置的浏览器都能触达设备。WebSocket 全双工、低延迟，适合控制指令与视频分片这类双向流式场景；MQTT 更适合传感器上行但做流式（视频/语音）不便；WebRTC 需 STUN/打洞，嵌入式实现复杂。三层中继是一个务实且可落地的架构选择。

## 二、感知与控制算法

**Q3：环境模式的开关窗决策是一套多层规则（安全优先 → 温差 → 投票），为什么不上机器学习？可解释性与精度如何权衡？**

答：规则（烟雾/雨水超阈值立即关窗、温差判断空调场景、多因素加权投票）具备**可解释、可调、可在 MCU 边缘实时运行、零训练成本**等优势。安全类规则（烟雾关窗、下雨关窗收雨棚）必须确定性触发，不能交由黑盒模型。学习能力由自适应模式承担——时间桶统计 + 传感器偏移做轻量预测，云端 DeepSeek 增强。整体是「规则保安全、学习做优化」的分层设计。

**Q4：自适应模式的「学习」本质是什么？如何防止学偏（如用户偶尔误操作）？**

答：本质是**统计而非深度学习**——把历史操作按 24 小时分桶，每桶计算平均角度，取记录最多的桶生成预测计划，置信度 = 桶记录数 / 总记录数，样本不足 5 条时回退不预测。它学习的是用户习惯而非复杂非线性映射。防学偏方面，置信度门槛与样本量下限是基础保护；进一步可对偏离均值过大的操作做降权过滤，属后续增强方向。

**Q5：自然风模式如何用舵机「找风」？120° 扫描本身是否会扰动气流、污染测量？**

答：原理是让百叶窗在 30°~150° 之间**慢速平滑扫描**（单程约 20 秒），每个角度由微型马达 + 风扇发电，经 ADS1115 采样电压换算为 0-100% 风速，逐角度多次采样取平均，最终锁定风速最大的角度作为最佳朝向。慢速扫描是为减小舵机动作对气流的扰动，同时每角度停留采样、读失败自动跳过，保证数据质量。

**Q6：若某个传感器读数异常（如温湿度读到 0），系统会不会误动作？**

答：这是容错设计的重点。环境模式在室内温湿度**读失败（读到 0）时会跳过决策、保持扇叶当前角度不变**，不把 0 当作真实环境值去误判关窗；烟雾/雨水/气流读数失败时保留上一次有效值。雨棚的「下雨展开」为独立逻辑，不受温湿度读失败影响。由此保证单点传感器故障不会导致窗户乱动。

## 三、智能交互

**Q7：语音交互哪些在本地、哪些在云端？断网时语音是否仍可用？**

答：唤醒词（WakeNet）与固定命令词（MultiNet，如「打开/关闭窗帘」）在**设备本地离线识别**，断网仍可用；自然语言理解（NLP）与复杂意图解析走云端 DeepSeek，断网时降级为本地命令词。TTS 语音合成同样在本地完成。基础功能不依赖网络。

**Q8：摄像头视频流如何传到外网浏览器？带宽量级多大？**

答：摄像头经 MIPI-CSI 采集 → 硬件 JPEG 编码（quality 40）→ Base64 → 按 3KB 分片 → WebSocket 发至云中继 → 广播给浏览器 → 浏览器拼片还原为 `<img>` 显示，约 15-20fps。单帧 JPEG 约几十 KB，上行约 1-2 Mbps。分片是为规避 WebSocket 大消息与中继 JSON 重序列化问题。多设备部署时需降帧率或按需推流控制带宽。

## 四、可靠性与安全

**Q9：云中继服务器是单点吗？服务器宕机后设备是否仍可用？**

答：中继确存在单点风险，是原型阶段的取舍。设备端自身具备本地 LVGL 屏 UI、本地语音、本地定时器与环境模式，**中继断开后仍能本地自主运行**，仅天气推送、AI 建议、外网 Web 控制等云端功能降级。生产化方向为服务器多实例 + 负载均衡。

**Q10：视频画面与麦克风音频均需经云服务器，WebSocket 是否有鉴权？数据是否加密？DeepSeek 的 API Key 是否硬编码在服务端？**

答：这是必须正视的短板——当前 WebSocket 仅做简单的 device_id 注册，无强身份认证，传输未加密，DeepSeek API Key 硬编码于 `relay_server.py`。这是原型为跑通功能所做的简化。正式部署需补充 Token 鉴权、TLS 加密，并将密钥迁移至环境变量/密钥管理服务；隐私层面也需向用户明确告知音视频会上云处理。

**Q11：6 路舵机 + 屏幕 + 摄像头 + 音频同时工作，整机功耗与舵机堵转保护如何考虑？**

答：舵机采用 MCPWM 独立通道控制，规避 LEDC 时钟分频冲突，每路 50Hz PWM，配合 0-180° 角度限位与按需驱动。堵转电流检测与睡眠低功耗为后续优化点——这是 IoT 项目常被忽视的工程问题。

## 五、创新提炼

**Q12：相较市面智能窗帘（Aqara、小米等），最具差异化的创新点是什么？请一句话概括。**

答：现有产品多为「单点遥控开关」，本项目做的是**多传感器融合的多模式自主控制**——环境温差决策、自然风自动朝向、时间习惯自适应、边缘语音 + 视频一体化，让窗户从「被控制」走向「会判断」。其中「自然风模式自动寻找最佳通风角度」与「环境温差决定开关窗」是相对有辨识度的差异化点。

## 附：一句话定位（电梯陈述）

灵窗智控通过边缘计算与多传感器融合，让窗户能够自主感知环境、学习用户习惯、响应语音指令，实现从「遥控开关」到「智能决策」的升级。

为什么有自然风模式？
1. 固定角度不一定是最大通风角。环境模式里百叶角度是由温湿度/光照算出来的 0–90°，它关心的是「该不该开、开多大」，不关心风从哪边吹。但自然通风的进风量对扇叶朝向高度敏感——扇叶迎风面和风向有个夹角关系，转错角度，即便开着风也进不来。
   
2. 风向是时变的。楼宇间、不同时段风向风速都在变，靠人工判断或者一次性校准没有意义。所以需要一个在线测量 + 自动锁定的闭环。
